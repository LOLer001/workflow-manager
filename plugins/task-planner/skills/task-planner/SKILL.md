# Task Planner

把用户当前消息描述的实际任务转成可审阅、可执行的 Markdown 计划。计划保存并展示后结束当前回合；用户明确批准当前版本之前，不开始任务。

## 启用边界

- 只响应用户在当前任务消息中的显式 `$task-planner` 调用或等价的产品显式调用信号。仅提到、引用、评审或开发 Task Planner 不算调用。
- 启用后，同一待确认任务的修改、确认与执行回复无需重复调用。任务完成或取消即结束本流程；无关的新任务不继承旧计划或授权，也不因历史调用而自动启用。
- 该 skill 是指令约束，不承诺用 hook 技术强制流程。宿主和 Workflow Manager 的审批仍有独立效力。
- Task Planner 不替换、不降级 Workflow Manager，不读写其状态、journal、hook 或合同，也不伪造其授权。

## 第一阶段：只生成计划

1. 先记住本会话原始工作目录。只做形成可执行计划所必需的、有界的只读检查或澄清。
2. 禁止执行实际任务、测试、构建、安装、部署、发布、写目标代码或启动执行代理。不得因为用户在同一条初始请求中写了“随后执行”等措辞而越过确认。
3. 根据任务复杂度安排步骤数量，不强制固定模型、角色或代理数量。每一步必须写明：动作、对象或路径、依赖、产出、验收标准。
4. 计划还必须写明目标与范围、必要前置假设、验证方案、关键风险与撤回办法，以及确认区。使用 [计划模板](references/plan-template.md) 调整结构，不机械复制占位内容。

## 保存与展示

- 若宿主明确提供本会话 `outputs` 目录，保存为 `outputs/task-plan-<简短题名>-v1.md`；否则保存在会话原始工作目录根部。即使后续读取源码时切换目录，也不得把计划误存到源码仓库。
- 文件名使用安全、简短、可辨识的题名。目标文件已存在时选择不会覆盖任何既有任务的唯一名称。
- 计划状态初始为“待确认”。保存成功后，向用户展示当前版本的实质内容和可点击路径，然后结束回合，等待确认。
- 写入被 Workflow Manager、宿主权限或其他限制拒绝时，报告目标路径和具体阻碍，并在回复中展示计划草稿；不得声称已经保存，不得执行任务。只有计划实际写入且已展示，才满足 Task Planner 的确认前提。

## 识别确认与修改

- 仅接受用户在后续聊天中，对当前实际已保存并展示计划的明确执行同意。问句、否定、条件表达、引用他人话语、沉默，以及仅编辑计划文件，都不是同意。
- 用户要求修改时，保留旧版并生成递增版本，再展示并等待确认。不得以旧版确认执行新版。
- 同一条消息同时要求修改和执行时，先保存并展示修改后的新版，再等待确认；不得把尚未展示的新版当作已批准。
- 确认后先把计划状态更新为“已批准”，再按批准范围执行。恢复或压缩上下文后，必须同时读取计划和聊天中的批准记录；Markdown 中由模型写入或人工修改的“已批准”不能单独证明授权。

## 执行中的范围控制

- 若目标、范围、风险类别或不可逆外部变更发生实质变化，写出新版本并重新确认。
- 已批准范围内的修复、重试和验证可以继续，无需重复索取 Task Planner 确认。
- 只有批准后，才可按宿主和 Workflow Manager 的允许决定是否委派；Task Planner 本身不强制模型或角色数量。

## 与 Workflow Manager 协作

- Simple 或原生任务也必须先完成本 skill 的保存、展示与确认流程。
- Hard 任务仍遵守 Workflow Manager 的只读评估、宿主证据和授权流程。Workflow Manager 可以自行把同一份已展示计划关联到其 canonical contract，并在规则允许时识别同一条聊天确认；Task Planner 不转换或伪造该授权。
- 若 Workflow Manager 的独立 gate 未满足，保留已经取得的 Task Planner 同意，不反复要求用户确认 Task Planner；说明具体的 Workflow Manager 阻碍，待宿主接受后继续。
